# Calidad, pruebas y seguridad

Objetivo: demostrar que la API y el frontend funcionan con pruebas automatizadas y calidad reproducible antes de que el usuario haga push a `main`.
Rama: `feature/calidad-pruebas-seguridad`; entrega por unidades de trabajo con commits conventionales en español; `chain_strategy=feature-branch-chain`; el push y la creación de PRs quedan en manos del usuario.
Entorno de pruebas: `uv` + `pytest`, con `pytest-cov`, Ruff y Bandit; Docker no es obligatorio para esta entrega.

## Specs

- **S1** — pytest: framework para escribir y ejecutar pruebas. El usuario pidió: "testear de que realmente funcione antes de que se aga pusk a main". La entrega debe cubrir con pruebas públicas el backend y el frontend, y la suite completa debe pasar antes de habilitar el push.
- **S2** — Ruff — no "Ruf": linter y formateador de Python. Debe ejecutar las mismas reglas localmente y en GitHub Actions.
- **S3** — Bandit — no "Bandati": análisis estático de seguridad. Debe ejecutarse sobre el código Python del repositorio y finalizar sin hallazgos pendientes.
- **S4** — pre-commit: ejecuta validaciones antes de cada commit. Debe cubrir formato, lint, seguridad y pruebas, y ser instalable con `uv run pre-commit install`.
- **S5** — GitHub Actions: automatiza las validaciones mediante CI. El workflow debe instalar el entorno bloqueado con `uv` y ejecutar Ruff, Bandit y pytest con cobertura.
- **S6** — Opcional pero recomendable: pytest-cov para medir cobertura. La ejecución de pytest debe producir un reporte de cobertura de backend y frontend.
- **S7** — "yo tengo uv es mejor que pip para crear entornos virtuales". El proyecto debe usar `uv`, versionar `uv.lock` y permitir comandos reproducibles con `uv sync` y `uv run`.
- **S8** — "los comit deben ser cortos sencilos en español con commit convencionales". Cada unidad de trabajo se entrega en un commit con tipo conventional y asunto breve en español; los tests acompañan al comportamiento que verifican.
- **S9** — "no necesitamos que se vea bonito el frontend solo que funcione sus funcionalidades". El frontend debe generar y devolver un PDF válido, usar correctamente la URL del backend y manejar fallos de conexión y timeout; no se agregan mejoras visuales. El usuario aclaró: "ya esto es un trabajo universitario, no daria decirte si si o si no, pero nos puede servir imagino por si nos falla algo no? cuando lo testee"; el debugger de Flask debe quedar disponible de forma opt-in mediante `FLASK_DEBUG=1` y desactivado por defecto.
- **S10** — "no hace ffalta que toquemos el readme, ese ignorale de momento". `README.md` no debe modificarse en esta entrega.
- **S11** — "yo no tengo docker compose ... me da flojera pero si toca toca". No se instala Docker ni se exige Docker local para probar; `uv` cubre el entorno de desarrollo. La integración se valida ejecutando los servicios Python localmente.
- **S12** — "quiero que alli tu me guies paso por paso sencillo para que enteienda como va funcionando y como lo testeo y valido que todo funciona". El cierre debe explicar el flujo local, cada comando de validación y cómo interpretar sus resultados antes del push.
